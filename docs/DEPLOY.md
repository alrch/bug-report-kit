# Развёртывание Bug Report Kit

Один экземпляр сервера и одна база данных обслуживают один проект. Его local,
dev, demo и production страницы подключают один и тот же скрипт и отправляют
карточки в этот экземпляр. Контур определяется по адресу страницы. Сервер не
угадывает ветку исходного кода: передавайте `data-app-version` с commit SHA
или release ID и задайте репозитории в конфигурации.

Это инструкция для Docker Compose и HTTPS-прокси на том же хосте. Команды ниже
подготавливают развёртывание; запускать их следует только после выбора хоста,
домена, места хранения резервных копий и доступа команды.

## 1. Конфигурация

На сервере клонируйте репозиторий, затем создайте локальный файл:

```sh
cp config.example.json config.local.json
```

В `config.local.json` укажите:

- `port: 7337`, `database: "./data/reports.sqlite"`;
- `projects[].id`, публичный случайный `widgetKey`, точные `allowedOrigins`
  (с протоколом и портом) для всех контуров, `repositories` с адресами кода;
- отдельные длинные случайные `teamTokens` для разработчиков и проверяющих,
  с нужной ролью и списком проектов;
- `trustProxy: true`, только если запросы приходят через ваш HTTPS-прокси,
  который **перезаписывает** заголовок `X-Real-IP` фактическим IP клиента.

Не коммитьте `config.local.json`, токены и SQLite-файлы. Публичный `widgetKey`
не даёт читать баги; приватный токен команды не вставляют в страницу. Если
прокси находится на отдельной машине или в контейнере, отдельно настройте
доступ к внутреннему порту и список доверенных сетей. Приведённый ниже Compose
открывает порт только на loopback хоста.

## 2. Запуск и HTTPS

```sh
docker compose build
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:7337/healthz
```

`compose.yaml` запускает Node 24, монтирует конфигурацию только для чтения,
сохраняет SQLite в именованном томе и перезапускает процесс после сбоя.
`BUG_KIT_HOST=0.0.0.0` действует только внутри контейнера; опубликованный порт
остаётся `127.0.0.1:7337` на хосте. `/healthz` проверяет ответ SQLite, но не
проверяет доступность внешнего HTTPS-адреса.

Пример блока Nginx в существующем HTTPS virtual host `bugs.example.com`:

```nginx
client_max_body_size 4m;
location / {
    proxy_pass http://127.0.0.1:7337;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Настройка сертификата и портов 80/443 остаётся в существующей инфраструктуре.
Не публикуйте порт 7337 напрямую в интернет. Проверьте внешний
`https://bugs.example.com/healthz` и открытие панели через HTTPS. Команда
входит в панель по имени и PIN. Для этого в проекте включите
`reporterAuth: true` и `panelAccess: true`; все зарегистрированные участники
этого проекта смогут читать тикеты и выполнять действия проверяющего. Для
публичного проекта с недоверенными авторами оставьте `panelAccess` выключенным
и выдавайте доступ через отдельный доверенный интерфейс. Приватные
`teamTokens` нужны API разработчика и агента и не вводятся в панель.

## 3. Подключение проекта

В общем шаблоне веб-приложения добавьте:

```html
<script src="https://bugs.example.com/widget.js"
        data-project-key="PUBLIC_WIDGET_KEY"
        data-app-version="COMMIT_OR_RELEASE_ID"
        data-reporter-name="ИМЯ_ТЕКУЩЕГО_ПОЛЬЗОВАТЕЛЯ"
        data-reporter-contact="КОНТАКТ_ДЛЯ_УТОЧНЕНИЙ"></script>
```

Подставляйте имя и контакт из активной учётной записи при формировании
страницы. Для SPA, где учётная запись может измениться после загрузки,
установите `window.__BUG_REPORT_KIT_REPORTER_PROVIDER__` перед загрузкой виджета;
функция возвращает только `{id, name, contact}` и вызывается при открытии формы.
ID помогает команде различать авторов с одинаковыми именами. Если учётной записи
нет, имя можно не передавать: карточка будет помечена как «Анонимный пользователь».
Все эти поля приходят из браузера и не доказывают личность; доверенная
идентификация требует серверной авторизации приложения.

Браузер пользователя должен открывать `bugs.example.com`, а точный origin
приложения должен быть в `allowedOrigins`. Если скрипт отдают с другого адреса,
укажите `data-server-url="https://bugs.example.com"`. Для дополнительной
диагностики HTTP-ошибок можно включить `data-capture-fetch-errors="true"`:
виджет тогда наблюдает ошибки стандартного `window.fetch`, не меняя запросы.
Он сохраняет метод, путь без query, статус, длительность и значения
`X-Request-Id`/`X-Error-Id`, если они есть, но не сохраняет тела и остальные
заголовки. Это опция: сначала проверьте её с сетевым
слоем конкретного проекта. Для Axios/XHR и собственного журнала используйте
`BugReportKit.instance.recordDiagnostic(...)` (пример в README).

Если у приложения есть Content Security Policy, разрешите адрес сервера в
`script-src`, `connect-src` и `style-src` (виджет загружает `/widget.css`).
Снимок строится через DOM/canvas; особенно строгая политика может мешать
рендерингу снимка, поэтому проверьте его на реальной странице. Не ослабляйте
глобальную CSP вслепую.

Проверка после подключения: открыть страницу нужного контура, нажать кнопку,
выделить область, увидеть предварительный снимок, отправить тестовую карточку,
найти её в панели и открыть HTML-тикет. Повторить на каждом контуре, который
будет использоваться. Отдельно приложить пробный файл и проверить, что он скачивается
из карточки, не меняя снимок.

## 4. Резервная копия и обновление

Сервис использует SQLite в режиме WAL. Не копируйте только `reports.sqlite`
обычным `cp` во время работы: свежие записи могут быть в WAL. Для согласованной
копии используйте встроенный SQLite backup API:

```sh
docker compose exec -T bug-report-kit node scripts/backup.mjs /app/data/backup-before-upgrade.sqlite
docker compose cp bug-report-kit:/app/data/backup-before-upgrade.sqlite ./backup-before-upgrade.sqlite
```

Скрипт не перезаписывает существующий файл и проверяет целостность копии.
Перенесите её в защищённое хранилище вне сервера и проверьте, что она там
открывается. Планируйте регулярные копии и срок хранения в инфраструктуре
проекта. Перед обновлением всегда создавайте копию: сервер при старте может
применять миграции схемы.

Обновление после копии:

```sh
git pull --ff-only
docker compose build
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:7337/healthz
```

Затем откройте панель, прочитайте прежний тикет и создайте пробный новый.
Для восстановления остановите сервис, сохраните нынешнюю базу вместе с файлами
`-wal`/`-shm` отдельно, поместите проверенную копию как `reports.sqlite` в том
данных, запустите сервис и повторите проверку. Восстановление перезаписывает
данные после даты копии; выполняйте его как отдельное осознанное действие.

## 5. Навык агента

Навык находится в `skills/process-bug-report/`. В локальном Codex его можно
подключить ссылкой на каталог навыка из этого репозитория (если такого навыка
ещё нет в личном каталоге):

```sh
ln -s "$(pwd)/skills/process-bug-report" ~/.codex/skills/process-bug-report
```

Для агента отдельно предоставьте `BUG_KIT_URL` и приватный токен роли
`developer` через окружение или менеджер секретов; токен не сохраняйте в
репозитории и не передавайте в командной строке. Проверка соединения:

```sh
node scripts/bug-kit-agent.mjs me
node scripts/bug-kit-agent.mjs projects
```

Агент приступает к багу только по явному поручению. Он читает карточку и
снимок, правит приложение, записывает результат и передаёт карточку на
проверку. Закрывает её проверяющий после приёмки.
