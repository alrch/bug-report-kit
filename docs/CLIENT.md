# Общий клиент SPA и отдельные установки Kit

## Что общее и что изолировано

Общий исходник — `widget/client.js`, `widget/loader-core.js` и `loading-ui.js`
в этом репозитории. `npm run build` создаёт автономный ES-модуль
`dist/client.mjs` с декларацией `client.d.mts`. Capture/SDK остаётся ленивым:
клиент загружает `/widget.js` и ждёт его CSS с сервера данного проекта.

У каждого проекта остаются свой процесс/контейнер Kit, config, SQLite, вложения,
приватные API/панельные токены и резервные копии. Рабочие и личные проекты
не используют общее хранилище, секреты и сеть доступа только потому, что
получили одинаковый код. На одном VPS можно разместить отдельные сервисы,
но нельзя использовать один volume/путь БД для разных проектов.
Общий клиент сам не создаёт и не переносит сервисы. Проверка кода не доказывает
изоляцию уже работающих серверов или резервных копий.

Версию клиента и серверного Kit закрепляет owning-проект. Рабочая и личная
группы обновляются отдельными выпусками: нет автоматического перехода на latest
или единого сервера обновлений. Обновление браузерного клиента само не меняет серверный pin, политику доступа
или схему БД. Первое внедрение этого API требует согласованной версии
клиента и SDK/сервера Kit из выпуска с этой правкой: старые SDK без BFCache-фикса
могут сохранять текст формы, но отключать её отправку после возвращения.
Совместимость нового клиента с произвольными прежними server pins не подтверждена.
До выпуска канонической ревизии кандидат не устанавливают в действующее приложение.

## Использование

Скопируйте `dist/client.mjs` и `dist/client.d.mts` из проверенной точной ревизии
Kit в vendor-каталог приложения; сохраните repository, commit и SHA-256 обоих
файлов в проектном manifest. Не редактируйте vendor вручную. Для локального
кандидата явно фиксируйте базовую ревизию и diff, не выдавая его за опубликованный
релиз. Сервер также отдаёт `/client.mjs` и `/client.d.mts`, но незакреплённый
динамический import с живого адреса не заменяет воспроизводимую поставку.

```js
import {acquireKit} from './vendor/kit/client.mjs';

// Стабильная функция читает текущий аккаунт при открытии формы.
const getReporter = () => ({id: currentUser?.id, name: currentUser?.name});
const connection = acquireKit({
  serverUrl: '/bug-kit',
  projectKey: PUBLIC_WIDGET_KEY,
  reporterAuth: true,
  voiceEnabled: false,
  launcherStyle: 'compact',
  appVersion: APP_VERSION,
  getReporter,
});
connection.ready.catch(error => console.warn('Kit unavailable', error));
// При размонтировании: connection.release().
// При программном повторе: await connection.retry().
```

В React вызывайте acquire в effect и возвращайте release. Общий клиент не
зависит от React. Для каждой аренды ready — getter текущей попытки. Уже взятый
Promise не меняется: после retry нужно дождаться возвращённого Promise или
снова прочитать ready. Последний release отменяет pending JS/CSS, удаляет свой
индикатор/SDK и слушатели. Cleanup отложен на microtask: синхронный повторный
mount с теми же параметрами сохраняет SDK и черновик. После настоящего ухода
последнего потребителя черновик не обещается сохранять. Release идемпотентен;
использование освобождённой аренды запрещено.

Одна страница имеет один активный Kit. Совпадающие настройки получают аренды
одного экземпляра, в том числе из двух копий этого клиента. Другие endpoint,
projectKey, flags, appVersion, тексты, nonce или ссылка getReporter при активных
арендах дают явную ошибку, не меняя очередь. Смена конфигурации требует release
всех потребителей. Отложенный cleanup старого поколения не уничтожает новое.
Не вызывайте destroy глобального loader/SDK вручную при активных арендах.

Неизвестный действующий loader или SDK отклоняется и не уничтожается. Import
клиента сам не регистрирует глобальный API и не меняет чужую интеграцию.
Legacy `<script ...>` сохраняет прежнее поведение: повторный embed использует
уже активный экземпляр без строгой проверки конфигурации. Поэтому при миграции
нужно убрать прежний embed/owned loader с той же страницы. Смешивание этих двух
способов не поддерживается как способ сменить проект.

Адрес разрешён через HTTPS либо loopback HTTP; сохраняется префикс пути.
Адреса с credentials/query/hash, неизвестные опции и некорректные типы
отклоняются. В клиент передаётся только публичный widgetKey, никогда team token
или объект сессии. При отсутствии getReporter используется существующий
`window.__BUG_REPORT_KIT_REPORTER_PROVIDER__` с актуальным значением. PIN/auth,
voice, CSP nonce и условия включения выбирает адаптер; клиент их не угадывает.
CSP должна разрешать JS/CSS/API нужного Kit. Nonce задаётся вторым аргументом
`acquireKit(options, {nonce})`.

Ранний индикатор/ошибка/повтор — существующий loading-ui, без второго интерфейса.
Ошибка загрузки не освобождает аренду: доступен повтор нажатием индикатора.
Если адаптер отдельно получает config, он передаёт индикацию клиенту в том же
синхронном шаге acquire и освобождает свою config-индикацию. Config404/fallback
и запрет fallback при явной ошибке остаются проектными решениями.

Окончательный pagehide очищает loader. При pagehide persisted=true страница
сохраняет его для BFCache, включая незавершённый ввод. Синтетическая проверка
этих событий не является доказательством реальной заморозки всеми браузерами.

## Проверки и поставка

`tests/client.browser.mjs` проверяет аренды, StrictMode, несколько bundle,
конфликты, актуального автора, чужой SDK, late JS/CSS, повтор и настройки двух
страниц. `tests/loader.browser.mjs` сохраняет регрессии прежнего embed.
`tests/instance-isolation.test.mjs` использует два сервера с отдельными временными
БД, вымышленными отчётами и токенами: проверяет отсутствие перекрёстного чтения,
ошибки чужого ключа/origin и независимый перезапуск. Эти fixtures не обращаются
к рабочей очереди и не подтверждают реальные mounts/secrets/backups.

Переход проекта включает проверку adapter/env, removal прежнего loader,
компиляцию, один индикатор/виджет и форму в самом приложении, доступ к правильной
панели, отдельную фиксацию ревизии и штатную поставку. Публичный proxy allowlist
не расширяется до панели/API чтения. Если клиент vendor-ится, новые маршруты
client.mjs/client.d.mts в proxy не нужны. Откат: вернуть адаптер+vendor приложения
к его прошлой версии; БД и серверные данные этим изменением не мигрируются.

Паспорт/руководство обновляются в owning-проекте при принятии адаптера. В самом
Kit отдельные паспорт и продуктовое руководство пока не подключены; README,
WORKFLOW, DEPLOY и этот контракт являются текущей документацией, а не заменой
непроведённого паспортного аудита.
