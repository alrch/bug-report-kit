# Контракт багов

## Что делает виджет

Веб-проект подключает один скрипт и передаёт публичный ключ проекта. Тестировщик
выделяет область, передвигает и растягивает рамку, подтверждает ✓ или снимает
выделение ×. Снимок создаётся только после подтверждения. Можно продолжить без снимка.
Затем заполняет единое поле «Суть бага, шаги для воспроизведения и что ожидалось»
(до 4000 символов) вручную или голосом. Отправить можно только непустой текст. Виджет отправляет снимок,
адрес страницы, размер экрана, выделенную область, версию приложения, браузер
и до 20 последних ошибок JavaScript. При интеграции проект может добавлять
свои безопасные сведения о неудачных запросах: метод, путь без параметров,
HTTP-статус, ID запроса и время выполнения. Один файл любого формата до 5 МБ
сохраняется отдельно от снимка и не заменяет его. Сервер удаляет query-параметры адреса и скрывает известные секреты в
диагностике. Перед отправкой человек должен проверить снимок на личные данные.

Контур определяется автоматически по адресу: `localhost` и `127.0.0.1` —
`local`, другие адреса сохраняются именем домена. Проект определяется публичным
ключом. Для поиска нужного кода в конфигурации проекта можно указать список
репозиториев. Версию сборки лучше передавать как commit SHA или release ID.

## Карточка, которую читает человек и агент

Панель служит очередью разовых сообщений о багах. В основном виде показываются
суть, автор и время, страница, статус, снимок, вложение и, после исправления,
краткое резюме результата. Пустые поля не выводятся. История статусов и
технические сведения раскрываются по запросу; данные для агента остаются в API.
Отчёт за период доступен отдельно для просмотра уже исправленных багов.

`GET /api/reports/ID` возвращает JSON с ID, проектом, репозиториями, временем,
контуром, страницей, версией, названием, описанием, шагами, ожидаемым и
фактическим результатом, наличием снимка и вложения, именем и размером файла, диагностикой, статусом, приоритетом,
исполнителем, похожей группой, причиной, исправлением, ссылками на код,
проверками, записью приёмки и историей. Снимок читается отдельно через
`GET /api/reports/ID/screenshot`; отдельный файл — через `GET /api/reports/ID/attachment`.
`GET /api/reports/ID/html` даёт самодостаточный HTML-тикет со снимком и вложением. Для всех этих запросов нужна авторизация:
сессия участника проекта с `panelAccess: true` либо служебный токен команды.
Публичная ссылка без авторизации не раскрывает баг.

Сервер хранит факты о баге. Он не меняет код приложения сам. Агенту нужен
доступ к нужному репозиторию и отдельный навык обработки: прочитать карточку,
найти код, задать вопрос при недостатке данных, изменить приложение, выполнить
адресные проверки и записать результат. Этот навык будет отдельным шагом.

## Статусы и действия

| Действие | Кто | Из статуса | Результат |
|---|---|---|---|
| `triage` | проверяющий | `new` или `triaged` | `triaged`, приоритет |
| `claim` | разработчик/агент | `new`, `triaged` или старый `in_progress` без исполнителя | исполнитель закреплён; новый баг становится `triaged` |
| `start` | исполнитель | `triaged` | `in_progress` |
| `ask` | исполнитель | `triaged` или `in_progress` | открытый вопрос, статус сохраняется |
| `answer` | проверяющий | открытый вопрос | ответ в истории, работа продолжается |
| `resolve` | исполнитель | `in_progress` | `ready_for_check` |
| `accept` | проверяющий | `ready_for_check` | `closed` и время приёмки |
| `reject` | проверяющий | `ready_for_check` | `in_progress` с замечанием |
| `cancel` | проверяющий | `new` или `triaged` | `cancelled` с причиной |
| `reopen` | проверяющий | `closed` или `cancelled` | `triaged` с причиной |
| `group` | проверяющий | любой | связь с основным багом того же проекта |

Каждое изменение требует `revision` из последнего чтения. Устаревшее
изменение получает `409`, чтобы два участника не перезаписали друг друга.
Сессия участника в панели действует как `reviewer` только для его проекта.
Токен `developer` не может принять своё исправление. Токен `reviewer` не может
представить исправление за разработчика. Токен `admin` может выполнять обе
роли. Для старых конфигураций токен без роли временно считается `admin`.

`resolve` требует непустые причину, описание исправления, хотя бы один
репозиторий с ссылкой на коммит/PR и хотя бы одну успешно пройденную проверку
(`fixEvidence.checks[].result: "passed"`). Если проверка не прошла, агент
остаётся в `in_progress` и продолжает исправление.
`accept` требует комментарий о проверке. Это позволяет человеку принять
результат или вернуть его на доработку, а отчёту отличать «код написан» от
«исправление принято».

## Отчёт за период

`GET /api/summary?from=YYYY-MM-DD&to=YYYY-MM-DD&groupBy=environment`
возвращает число созданных багов, число принятых исправлений, статусы созданных
багов и группировки. `groupBy` принимает `environment`, `project` или `group`
(отпечаток похожего бага либо выбранный основной баг). Даты включительные;
период ограничен одним годом. Исправление попадает в период по времени
**приёмки**, а не по времени отправки агентом на проверку. Повторно открытый
баг перестаёт считаться принятым. `GET /api/summary/html` даёт читаемый
HTML-отчёт с причиной и результатом для принятых исправлений. Если их больше
500, HTML показывает первые 500 и явно сообщает об этом, а счётчики остаются
точными.

## Границы первой версии

- Предложение похожих багов строится по проекту, пути страницы и названию.
  Связь «дубликат основного бага» подтверждает человек; автоматического
  слияния нет.
- Сервер не знает ветку исходного кода по домену. Репозитории задаются на
  уровне проекта, а точный коммит передаёт приложение как версию сборки.
- Автоматически собираются ошибки JavaScript после загрузки виджета. Хост
  может передать свои события запросов через `recordDiagnostic`. Опциональный
  `data-capture-fetch-errors="true"` наблюдает неуспешные вызовы стандартного
  `fetch`; он сохраняет только метод, путь, статус, время и IDs из двух
  ответных заголовков, не читает тела и не охватывает Axios/XHR.
- Перед общим развёртыванием нужны HTTPS, защищённое хранение токенов,
  резервное копирование SQLite и проверка доступа к панели и API.

## Голосовое описание

Запись доступна через MediaRecorder в HTTPS или localhost; формат выбирается из WebM/Opus,
MP4 и Ogg/Opus. Максимум 120 секунд и 5 MiB; локальный декодер допускает 125 секунд
с учётом задержки кодера. WAV принимается сервером для совместимости.
Во время записи нижняя кнопка называется «Готово». Она или повторное нажатие микрофона
завершает получение последних аудиобайтов и запускает распознавание черновика.
Ни остановка, ни повтор распознавания не создают баг. Над нижними кнопками показывается отдельная синяя плашка «Идёт расшифровка…»
с круглой крутилкой; после вставки — галочка и «Расшифровка добавлена».
Она остаётся видна при прокрутке, новая запись/удаление очищают подтверждение.
«Отмена» остаётся доступной; микрофон освобождается. Модалка и единственное поле
сохраняются, нижние действия закреплены, содержимое прокручивается отдельно.

Машинный текст добавляется к текущему значению поля, включая изменения за время ожидания.
Человек проверяет и редактирует его перед окончательной отправкой. Счётчик показывает
4000 символов; длинная расшифровка сохраняется целиком, отправка блокируется до сокращения.
Пустой/пробельный текст не отправляется даже с аудио. При ошибке ASR сохраняются текст
и плеер оригинала; есть «Повторить распознавание» и ручной ввод. Недоступный микрофон
также оставляет ручной ввод. Ошибка отправки сохраняет форму и байты записи.

### Временный черновик ASR

POST `/api/transcription-drafts` принимает `{audio,pageUrl}`, возвращает 202 с `id`,
`draftToken`, состоянием и `expiresAt`. POST `/api/transcription-drafts/ID/status`
возвращает состояние; GET `/api/transcription-drafts/ID` оставлен для клиентов,
передающих Origin (браузерный same-origin polling использует POST).
POST `/api/transcription-drafts/ID/retry` повторяет failed/unavailable;
POST `/api/transcription-drafts/ID/cancel` удаляет черновик и останавливает его процесс.

Все операции требуют публичный `X-Project-Key` и разрешённый Origin, а при reporterAuth —
действующий `X-Reporter-Token`. Операции по ID дополнительно требуют `X-Draft-Token`.
Черновик привязан к проекту и постоянному ID авторизованного автора: повторный вход того
же автора сохраняет доступ, чужой автор/проект/токен получает 404. Гостю нужен отдельный
непредсказуемый draft token. Team token в виджет не передаётся.
Create/retry ограничены 6 попытками в минуту на project+IP; максимум 8 черновиков на проект.
Оригинал и результат временно находятся в отдельной SQLite-таблице `transcription_drafts`,
срок — 15 минут. Очистка выполняется по таймеру 2 секунды и при обращении; после перезапуска
истёкшие удаляются, прерванный lease возобновляется после timeout+10 секунд.
Закрытие формы отменяет запросы/черновик и исключает поздние изменения текста.
При утрате ответа create недоступный клиенту черновик убирается по TTL. Временные аудиокаталоги учитываются отдельным lease и удаляются в finally; после
аварии их убирает следующая очистка по истечении timeout+10 секунд, в том числе
после перезапуска. Очистка ограничена каталогами bug-kit-speech-* внутри OS tmp.

Один общий worker обслуживает черновики и прежние report_audio, без параллельного ASR.
Финальный POST `/api/reports` получает оригинал `audio`, проверенный автором `description`
и `transcriptionDraft:{id,token}`. Сервер проверяет совпадение аудиобайтов, переносит машинный
текст/состояние в `report_audio` и удаляет черновик в одной транзакции. Готовый результат
повторно не распознаётся. Если временный результат истёк во время редактирования,
форма сохраняет проверенный текст и аудио и явно предлагает отправить ещё раз
через совместимый API; только в этом случае ASR может выполняться после отправки.
При потере ответа polling повтор возобновляет чтение состояния, сохраняя тот же job.
Ручная отправка после сетевой ошибки прерывает ещё работающий draft и переносит
оригинал с состоянием failed без повторного ASR. Описание длиннее 4000 отклоняется явно, без обрезания.
Старый API аудио-only и прежние поля expected/actual/steps остаются совместимыми;
новый виджет требует текст и оставляет expected пустым.

Сохранённый оригинал, машинная расшифровка и исправленный человеком текст остаются
раздельными. GET `/api/reports/ID/audio` и POST `/api/reports/ID/transcription` требуют
проектной авторизации панели. Панель и HTML показывают оригинал и машинный текст;
CLI `audio ID NEW_FILE` выгружает оригинал. После финальной отправки автоматический
срок хранения оригиналов не настроен; очистка временных файлов ASR их не удаляет.
Состояния: pending, processing, ready, failed, unavailable.

### Локальный распознаватель

Установить Python 3.12, создать private venv и выполнить
`pip install -r scripts/speech-requirements.txt`. Заранее загрузить multilingual
модель faster-whisper (по умолчанию tiny) из официального Systran репозитория
в Hugging Face cache. При обработке сеть/загрузка модели не используются.
В приватном config задать `transcription.command` как массив: абсолютный путь
к Python, путь к `scripts/transcribe.py`, опционально `--model`, имя или локальный
путь модели. Для преимущественно русской речи добавить `--language`, `ru`: это
задаёт язык распознавания явно; без флага действует автоопределение.
Kit дописывает пути временных аудио и текстового файла. Shell
не используется. `transcription.timeoutMs` по умолчанию 300000, максимум600000.
Исходные аудио входят в штатный SQLite backup; веса модели и venv переустанавливаются.
Автоматическая расшифровка может ошибаться — оригинал остаётся доступен для проверки.
