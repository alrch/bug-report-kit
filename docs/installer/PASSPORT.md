# Технический паспорт: общий серверный установщик Kit

Паспорт описывает серверный Docker-установщик. Пользовательский смысл раскрыт
в [руководстве](PRODUCT_GUIDE.md), границы — в [справке](PROJECT_OVERVIEW.md).
Выполненные проверки и ограничения хранятся в [свидетельстве](evidence-2026-11-02.md).
Это описание установщика, а не полный аудит всех функций Kit.

## INS-01

### Подготовка и планирование

Уполномоченный оператор задаёт параметры одного экземпляра и запускает
`python3 scripts/deploy.py ACTION PRIVATE_DEPLOY_JSON`. В JSON нет команд и значений
секретов. Явный `--adapter /absolute/trusted/module.mjs` выбирает проверенный
проектный код: это граница доверия к коду, а не песочница.

Серверному входу нужны Python 3 и Docker; системный Node не является обязательным
предварительным шагом. Общий bootstrap выбирает доступный Node 24+, а при его
отсутствии на Linux берёт только публичный `/usr/local/bin/node` из уже принятого
неизменяемого локального образа Kit. Для этого создаётся отдельный остановленный
контейнер без mounts и запуска приложения, после копирования он удаляется по
проверенным ID/метке/образу. Библиотеки, config и файлы работающей службы не
копируются; скачивание, установка системных пакетов и изменение службы не нужны.

До копирования проверяются image ID, Linux/native architecture и размер одного
обычного tar-файла: максимум 256 MiB и свободное место размер файла плюс 64 MiB
резерва. Нет extract-all. Приватный временный каталог и ELF64-файл имеют владельца
оператора, права 0700, SHA и проверку версии перед запуском. Симлинки, чужие
каталоги, дополнительные tar-записи и несовместимые библиотеки хоста дают конечный
отказ. SHA копии обнаруживает её изменение; происхождение образа заранее принимает
owning-проект. Временный runtime удаляется после команды. Прямой Node CLI остаётся
доступным для разработки и уже подготовленной среды.

[Пример схемы](deploy.example.json) определяет допустимые поля. Неизвестные,
пропущенные и неверно типизированные поля отвергаются. Поддержан только профиль
`docker-server`. Образ уже должен быть загружен: принимаются `sha256:ID` и
`repository@sha256:ID`, не теги. Загрузка, сборка и проверка происхождения архива
остаются предварительным шагом. Установщик разрешает ссылку в фактический
неизменяемый локальный ID Docker; он не доказывает происхождение образа по тегу.

Файлы параметров/config и состояние приватны: 0600/0700, обычные файлы,
канонические абсолютные пути без симлинков. Оператор и выбранный UID контейнера
должны иметь необходимый доступ к config. Пути состояния, config и данных
не пересекаются. Каталог bind-данных существует и закрыт; named volume заранее
создан с нужным владельцем. Установщик не исправляет права существующих данных
и не создаёт реквизиты. Родитель каталога состояния уже существует и приватен.
Параметры установки и состояние принадлежат оператору. Для config и bind-данных
допустимы UID оператора либо явно выбранный runtime.uid; это не разрешает
принимать чужие файлы состояния.

Профиль требует явные UID/GID и непривилегированный порт 1024–65535, совпадающий
с config. Данные доступны как `/app/data`, config — `/app/config.local.json`.
Транскрибация и голосовые проекты запрещены, распознавание отключено. Приватные
значения не попадают в вывод; ошибки JSON/Docker/адаптера заменены конечными кодами.

`plan` читает параметры, идентичность службы и квитанцию, разрешает образ и
сообщает, требуется ли изменение. Состояние и backup не создаёт. `status`
показывает наличие службы, управление установщиком и необходимость восстановления;
здоровье службы этим не подтверждается. Квитанция закрепляет экземпляр, пути,
runtime, адаптер и digest config. Последующее изменение байтов config отвергается;
перепривязка и миграция конфигурации в этой версии не реализованы.

Источники: [Python bootstrap](../../scripts/deploy.py), [CLI](../../scripts/deploy.mjs),
[схема и приватные пути](../../runtime/deploy/config.mjs),
[Docker](../../runtime/deploy/docker.mjs),
[привязка состояния](../../runtime/deploy/installer.mjs).

## INS-02

### Установка и обновление

`install` создаёт отдельный контейнер либо регистрирует существующую службу,
владение которой доказал доверенный адаптер. Общий Docker-драйвер требует свои
метки и точные mounts; одного совпадения имени недостаточно. Проектный адаптер
может доказать владение прежней Compose-службой по проекту, сервису и mounts.
Для `update` нужна квитанция. При уже выбранном образе служба проверяется и
используется без пересоздания: повтор обновления не создаёт дубликат и не стирает
данные. Повторный `install` с тем же образом проверяет и использует службу без изменений.
Если запрошен другой образ, повторная установка отвергается: для смены версии
управляемой службы используют `update`.

Изменения удерживают приватный эксклюзивный замок экземпляра. Если приложение
имеет общий замок поставки, проектный launcher удерживает его всю операцию,
включая автоматическое восстановление. Перед сменой runtime установщик:

1. Сохраняет приватный долговечный backup config и данных с manifest завершения.
   SQLite копируется online API фактической предыдущей версии. Снимки, вложения
   и историческое аудио хранятся BLOB в SQLite; прочие файлы копируются без
   перехода по симлинкам. Незавершённый backup имеет `complete:false` и блокирует
   переключение.
2. Копирует backup в отдельный временный Docker volume. Запускает настоящий CMD
   кандидата с watchdog, проверяет HTTP, assets, целостность SQLite, исходные
   столбцы/строки всех прежних таблиц и хеши прежних файлов. Новые таблицы,
   столбцы и файлы допустимы; изменение прежних данных консервативно отвергается.
   Поэтому даже штатное удаление истёкшей временной записи может остановить пробу.
   Ожидаемые хеши и строки доступны проверке отдельным read-only mount вне
   изменяемой копии: кандидат не может переписать собственный эталон.
3. Запускает фактическую предыдущую версию на **той же изменённой кандидатом
   копии** и повторяет проверки. Чистой БД и одного integrity check недостаточно.
4. Повторно проверяет config, идентичность и защитную границу службы. Адаптер
   сохраняет точные прежние настройки, затем общий исполнитель записывает журнал
   и меняет только доказанно принадлежащую экземпляру службу. Проверяет образ,
   внутренний health и настроенный внешний health.

Временные контейнеры и volumes имеют случайные имена и метки владения;
перед удалением проверяются их метки/ID. Backup остаётся приватным в
`stateDirectory/backup-UUID`. Автоматическая очистка, шифрование, offsite-копия и
проверка восстановления рабочего сервера не заявлены. Копия config содержит
секреты и включается в принятую оператором политику приватного восстановления.

Внешний health использует HTTPS либо loopback HTTP, оканчивается `/healthz`,
не содержит реквизитов, query и fragment. Redirect отвергается. Общий драйвер
требует `{ok:true}`; проектный адаптер проверяет свою границу прокси. Квитанция
создаётся после проверки работающей службы; при неподтверждённом восстановлении
журнал сохраняется. Наличие исходников не означает поставку сервера.

Источники: [транзакция](../../runtime/deploy/installer.mjs),
[backup и пробный запуск](../../runtime/deploy/docker.mjs).
Прежние [supervisor](../../runtime/service.mjs) и
[серверный writer данных](../../server/app.mjs) остаются отдельными потребителями.

## INS-03

### Проверка, сбой и восстановление

`verify` требует стабильную квитанцию и проверяет фактические ID/образ контейнера,
внутреннюю готовность и внешний health. Незавершённая операция отвергается;
`status` не заменяет эту проверку.

После сбоя переключения установщик пытается вернуть фактическую предыдущую
версию и проверить её. `ACTIVATION_FAILED_RESTORED` означает неуспешное обновление
с подтверждённым восстановлением, а не поставку кандидата. При сбое восстановления
или health возвращается `RECOVERY_REQUIRED`, журнал остаётся. У первой установки
без прежней службы нет рабочего baseline для отката: может понадобиться оператор.

`recover` работает с журналом прерванной операции. Замок освобождается только
если доказано отсутствие сохранённого PID владельца; живой, повторно использованный
или недоступный PID остаётся блокировкой. Восстанавливаются сохранённая версия и
исходная защитная граница операции. Журнал удаляется после проверки результата.
Адаптер отвергает изменение соседей, файлов и mounts и при новом процессе.
Журнал без baseline даёт `RECOVERY_REQUIRES_OPERATOR`; без журнала recover
не меняет runtime. Недоступность зависимости не считается успехом.

`rollback` выбирает предыдущую версию последней успешной операции, сначала
проверяет её на свежей копии **текущих** данных и лишь затем возвращает код и
настройки адаптера. Новые отчёты и доступы, появившиеся после обновления,
сохраняются. Ни одна команда не восстанавливает историческую БД. Успешный явный
откат использует единственную сохранённую предыдущую цель; новое обновление может
создать новую. Backup доступен для отдельной разрешённой процедуры восстановления.

### Контракт доверенного адаптера v1

Модуль экспортирует `createAdapter({spec,docker,createComposeAdapter})`. `docker.run(args)` выполняет
ограниченный вызов Docker без shell и захватывает вывод, который нельзя печатать.
Адаптер возвращает:

- `identity` — стабильный ID, включаемый в привязку состояния.
- `inspect()` — null либо `{id,imageId,imageRef,guard?}` с полными ID.
  `guard` — ограниченный приватный JSON с защитными метаданными без секретов.
- Необязательный `prepare({image,expected,guard})` сохраняет точные прежние
  настройки до общего журнала. Вызывается для install/update, не явного rollback.
- `activate({image,expected,rollback,guard})` сравнивает текущую идентичность,
  применяет точный образ, сохраняет config/данные/соседей и обслуживает прокси.
  `rollback:true` возвращает сохранённые точные настройки адаптера.
- `verify({imageId,guard})` подтверждает образ и готовность с исходной защитной
  границей. Recover получает guard из журнала, не принимает нынешних соседей
  за прежних. Новая независимая операция может зафиксировать законно изменённых
  соседей заново.

Для Compose общая фабрика [createComposeAdapter](../../runtime/deploy/compose.mjs)
содержит проверки владения и соседей, сохранение точных настроек, переключение
и перечитывание nginx. Проектный модуль передаёт ей фиксированное описание
своих ресурсов. Данные deploy JSON не могут подменить фабрику или это описание.
Исходный Compose проверяется как канонический обычный файл без записи для
группы/остальных и с владельцем root либо оператора. Приватные env/override/config
имеют свои более строгие правила. Закрытый родительский каталог сам по себе
не даёт права принять неизвестного владельца исходного файла: существующие
дескрипторы или другая ссылка на inode могут сохранять внешнюю запись.
Проектный launcher обеспечивает прежний общий замок и выбор доверенного модуля.
Данные JSON не содержат исполняемых команд. Установка и права адаптера принадлежат
owning-проекту; импорт произвольного кода не является гарантией изоляции.

### Покрытие и ограничения

Сценарии: [контрольные тесты](../../tests/installer.test.mjs),
[проверки общего Compose-адаптера](../../tests/installer-compose.test.mjs) и
[настоящий Docker](../../tests/installer.docker.mjs). Данные вымышленные;
приёмку реального бага эти проверки не доказывают. Свидетельство разделяет
ревью исходников, исполнение, интеграцию Roof и рабочую поставку. Native/macOS,
голос, управление несколькими хостами, получение образов, ротация секретов
и полный паспорт остальных функций Kit остаются за границей этого раздела.
